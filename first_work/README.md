这次作业分为两个部分：cmake和linux
这次 CMake 作业一开始其实我挺懵的，因为之前自己尝试写C++项目更多就是单文件或者几个文件一起编译，没有真正认真想过一个工程里面这么多目录、这么多模块到底是怎么被组织起来的，总是认为一个大工程下就应该放在同一个文件夹下面，头文件就该和主文件放在一起。后来发现我想的太简单了。刚开始看到根目录、common、modules，还有每个模块下面自己的 CMakeLists.txt，我的感觉就是：这些文件好像都在写 CMake，但是每个文件到底负责什么，我分得不是很清楚。后来慢慢看下来才知道，根目录的 CMakeLists.txt 更像是整个工程的入口，负责设置工程名、C++标准、添加子目录，最后生成可执行文件；common和modules下面的CMakeLists.txt主要负责继续向下管理子模块；真正到A1、A2、M1、M2这种具体模块的时候，才是把src里的cpp收集起来，用add_library编译成静态库，再用target_include_directories暴露自己的头文件路径，用target_link_libraries说明自己依赖谁。
这个过程中我踩了不少坑。最开始add_subdirectory找不到目录，是因为我没有意识到它是相对于当前CMakeLists.txt的路径去找子目录的，所以工程根目录和运行cmake的位置很重要。后面又遇到target重名的问题，才知道CMake里的target名字不是随便写的，同一个工程里面每个add_library或add_executable创建出来的 target 都必须唯一。再后来就是各种头文件找不到，比如A1.h、A2.h、KalmanFilterX.hpp，这些问题一开始看起来都是“文件明明在那里为什么找不到”，后来才明白CMake 不会自动帮你猜头文件在哪里，必须通过 target_include_directories把对应模块的include路径加进去。这里我也慢慢分清了CMAKE_CURRENT_SOURCE_DIR和PROJECT_SOURCE_DIR的区别，前者是当前这个CMakeLists.txt所在的目录，适合找本模块自己的include；后者是整个工程根目录，适合跨模块找其他模块的头文件。
还有一个比较重要的点是include和link的区别。刚开始我会把target_include_directories和target_link_libraries混在一起理解，觉得都是“让模块能用起来”。后来通过OpenCV（其实这个东西主要还是用find_package）的报错才真正分清楚：include主要解决的是编译阶段找头文件的问题，比如fatal error: xxx.h没有那个文件或目录；link解决的是链接阶段找实现的问题，比如undefined reference。OpenCV这里就很典型，KalmanFilterX.hpp里面包含了opencv2/core.hpp，所以使用kalman的模块不仅要能找到kalman的include，还要能找到OpenCV的include；但是光能找到头文件还不够，最后如果没有把OpenCV_LIBS链接进去，还是会在链接阶段报undefined reference。这个错误反而让我对C++的编译流程更清楚了：先通过include找声明，编译成目标文件，最后再通过link找真正的函数实现。
这次作业里kalman模块也让我理解了header-only的情况。它本身没有src，也没有cpp，所以它不像A1、A2、M1、M2那样生成静态库。它更像是一个只提供头文件的公共模块，所以不能简单地把它当成libkalman.a去链接，不然就会出现找不到-lkalman的错误。对于这种模块，重点不是add_library生成库，而是把它的include路径正确传递给真正使用它的模块。如果它内部又依赖OpenCV，那么使用它的模块也要处理OpenCV的include和link。
整体做下来，我感觉这次作业最大的收获不是单纯把程序跑通，而是对一个多模块 C++ 工程的构建逻辑有了具体感觉，现在至少能知道每一层 CMakeLists.txt 大概在干什么：根目录负责统筹，modules/common负责组织子模块，具体模块负责编译库和声明依赖。遇到报错的时候，也能先判断它是目录问题、头文件路径问题、target重名问题，还是链接库的问题。虽然很多语法还不能说完全熟，但我已经能顺着工程结构去分析已经写好的CMake，然后再打（代码）出自己的风采。
