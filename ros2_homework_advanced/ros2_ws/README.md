这应该是我实习以来做过的最难的任务，也是第一个让我觉得可能做不完的任务。
ROS2真的是一个非常精妙的工程。它比ROS最明显的升级就在通信系统上——它不再像ROS1那样自己实现TCPROS/UDPROS通信协议，而是基于DDS（数据分发服务）架构来实现通信。它取消了核心的Master节点，让每一个节点自行工作、自行发现彼此并发布话题。就算某个节点出了问题，也不会影响大局。
整个ROS2是一个非常工程化、体系化的项目。它不像之前的作业，只掌握一门编程语言就能胜任。你需要同时面对rclcpp写节点逻辑、用CMakeLists配置编译规则、在package.xml里声明依赖，每一步出问题都会卡住。而且ROS2的结构不是集中式的，它非常分散——每个节点各管各的，通过话题、服务、动作来通信。这种形式对车辆这种多模块系统很友好，各个关节可以灵活沟通，但作为初学者，很难一下子在脑子里建立起整体印象。
这里在实现上比较困难的就是进阶作业——要写一个节点，订阅/estimation/slam/map话题拿到的Map消息，然后把里面的锥桶坐标提取出来，一个一个封装成Marker再发布出去，最后让RViz接收这些Marker来完成可视化。
现在基础作业做出来了，但进阶作业卡住了。说句实话，基础作业其实还好。画8字形那个，主要就是搞清楚turtle的消息格式和转向参数。我用的geometry_msgs/Twist，线速度和角速度配合着调，先往一个方向转圈，画完一个圆之后再反向，两个圆就相切了。单源文件、单功能包，编译跑通就能看到乌龟在画8字，这个难度还在可控范围内。真正让我觉得吃力的，是进阶作业。
进阶作业要做的事情说起来也不复杂：用ros2 bag play播放给定的bag文件，然后写一个节点订阅/estimation/slam/map话题，把收到的Map消息里的锥桶位置一个个转成Marker，再发布出去让RViz显示。就这一句话的事，我折腾了好几天，到现在都没跑通。
首先就是fsd_common_msgs这个功能包的编译问题。它本身没有源文件，只是定义了一套消息格式，理论上直接编译就能用。但我第一次colcon build的时候，在rosidl_generate_interfaces阶段就报错了，提示msg生成IDL过程中缺少文件。我当时下意识觉得是自己的CMakeLists或者代码写错了，反复检查了好几遍，甚至还去折腾can_msgs的依赖问题。后来才慢慢意识到问题可能出在消息生成机制本身——ROS2里.msg文件要先转成.idl，再从IDL生成代码，中间任何一个环节卡住都会报错。但问题是，我到现在也没找到到底是哪个环节卡住了。清理build和install目录重新编译试过了，不行；检查msg文件是不是有问题，看起来也没毛病。就卡在这里，每次colcon build都是同一个错误，特别搞心态。
编译一直过不了，整个进阶作业就动不了。后面的bag播放、节点运行、RViz可视化，都还没机会去验证，只能先把MarkerPublisher的代码逻辑写好放在那里。这种感觉特别难受，明明知道思路是对的，但工程问题就横在前面绕不过去。之前做深度学习的时候环境配置再折腾，至少还能先把代码跑起来看效果，这次连运行都运行不了。
虽然还没实际跑起来，但我在写代码和查资料的过程中已经预感到，就算编译通过了，后面可能还会有一堆问题。比如我对rosbag、topic、RViz三者之间的数据流关系根本不清晰。出了bug的话，应该先确认bag是不是在正常播放，topic有没有数据，最后才看RViz的配置和代码逻辑——但我之前根本没这个意识，出了问题第一反应就是去改代码。整个ROS2的调试链条太长了，一个环节不通就全卡住，而我现在连第一个环节都没过去。
一直卡在编译阶段，让我被迫花了很多时间去搞清楚ROS2的消息机制到底是怎么回事。之前做基础作业画8字形的时候，用的是geometry_msgs/Twist，那是ROS2自带的通用消息类型，直接include就行，根本不用自己编译消息。所以我对"自定义消息要单独编译"这件事完全没有心理准备。
现在回头看，fsd_common_msgs这个功能包其实就是一个纯接口包。它在ROS2里的角色很特殊：没有源文件、没有节点，只有msg定义和package.xml。它的唯一作用就是定义一套消息格式，让其他功能包可以引用。这种设计在ROS2里非常常见，车队项目里尤其多——因为不同的节点之间需要约定好统一的数据格式，而这些格式本身就需要作为一个独立的功能包来维护。我一开始没意识到这一点，总以为功能包里一定要有cpp文件才算完整，看到fsd_common_msgs里只有msg文件夹的时候还愣了一下。
再往深说，ROS2对消息的处理流程也比我想象的复杂。一个.msg文件不是直接编译成代码的，中间要经过rosidl这套接口生成层。具体来说，先由rosidl_adapter把.msg文件转成.idl文件（接口定义语言），然后再由不同语言的代码生成器把.idl转成对应的头文件和源文件。C++的代码生成器是rosidl_typesupport_cpp，Python的是rosidl_typesupport_python。所以报错出现在rosidl_generate_interfaces阶段，意味着问题很可能出在.msg到.idl这个转换环节，或者是后续代码生成器的配置出了问题。但知道归知道，具体卡在哪里我还是没找到。
还有一个让我意识到的事：ROS2的编译系统是真的严格。你功能包如果写错了CMakeLists，或者package.xml里的依赖没声明全，不会给你任何"容错"的空间。find_package找不到？直接报错停下。消息生成失败？整个build停止。这跟之前用Python写深度学习完全是两回事，Python你import错了至少还能一行行试，ROS2的编译报错经常是一面墙一样的日志砸下来，得一行行翻才能找到真正有用的那几句。
说回来，虽然编译还没过，但在这个过程中我至少搞明白了一件事：fsd_common_msgs提供的Map消息结构是理解车队数据流的关键入口。Map消息里包含了不同颜色的锥桶列表，还有map的header信息。如果将来编译能过，我的MarkerPublisher节点只要正确订阅这个Map消息，把每个锥桶的位置提取出来生成Marker，理论上RViz就能显示。但现在，一切都卡在第一步。
